# DeepSeek、豆包与 OpenAI 产品场景评测方案

日期：2026-08-11
状态：评测方案已准备。产品先实现 DeepSeek、豆包和 OpenAI 三个 provider，再配置凭据并执行真实调用。

## 目标

不要用通用排行榜决定模型，而是比较三个候选模型在 English Companion 的真实任务中谁更适合：

1. 中文 → 简短、口语化、适合 Slack/WhatsApp 的英文，并提供忠实中文回译。
2. 英文 → 中文翻译，并生成不过度承诺的建议英文回复。
3. 英文优化 → 同时输出原文、自然修改版和准确的逐项说明。
4. 中文及中英混杂优化 → 中文变得更清晰，或将混杂草稿整理成连贯英文，同时保留技术标识。

候选 provider：

- DeepSeek
- 豆包 / Volcengine Ark
- OpenAI

## 公平性原则

- 三个模型收到完全相同的 system prompt、输入和结构化输出要求。
- 使用各家适合低延迟日常文本任务的非推理/聊天模型；不把昂贵推理模型与轻量模型直接混比。
- 固定低随机性；每条案例至少运行一次，出现明显不稳定时重复三次。
- 输出先匿名化为 A/B/C，Kris 不看模型名进行选择。
- 不使用某一个参评模型单独担任最终裁判。
- 自动规则只能检查格式、事实保留和响应时间；自然度与可发送性由 Kris 盲选。

## 测试集

目标为至少 30 条匿名化真实案例，在四种工作流之间尽量均衡；不足时优先保证场景多样性，而不是凑数。

### A. 中文 → 英文

覆盖：

- 请求确认
- 推迟或改期
- 主动提供帮助
- 汇报验证结果
- 表示同意或保留意见
- 催进度但不显得生硬
- 技术术语、日期、人名占位符和链接

### B. 英文 → 中文 + 建议回复

覆盖：

- 同事请求验证
- 迁移时间协调
- 不完整或带语法错误的工作消息
- 含隐含行动项的信息
- 只需确认收到、不应作额外承诺的信息

### C. 英文优化

覆盖：

- 缺主语或冠词
- 时态和单复数
- 中式英语
- 可以理解但不自然的搭配
- 过度正式
- 过度简略
- 已经正确、不应被过度修改的句子

### D. 中文与中英混杂优化

覆盖：

- 冗长或不清晰的中文工作消息
- 中文技术说明的精简
- 大量中文夹少量英文项目名/命令
- 大量英文夹中文意图片段
- 不得翻译或改写的 URL、命令、项目名和缩写

现有历史中已有少量可匿名化种子案例，例如：

- `Is there anything need from our end?`
- `Sure, may I know what kind of issue? Do you need our help?`
- `I will let you know before migration starting.`
- `Already migrate to the new cluster, can you try?`
- `这个方案我需要再看一下，晚点回复你。`
- `麻烦你确认一下这个版本是否可以发布。`

在正式评分前仍需补齐更多真实案例，避免测试集被少数迁移场景主导。

## 输出契约

### 中文 → 英文

```json
{
  "english": "可直接发送的简短英文",
  "backTranslationZh": "忠实反映该英文实际含义的中文回译"
}
```

### 英文 → 中文

```json
{
  "translationZh": "自然中文翻译",
  "replyNeeded": true,
  "suggestedReplyEn": "简短建议回复，若无需回复则为空"
}
```

### 英文优化

```json
{
  "improvedEnglish": "优化后的英文",
  "changes": [
    {
      "original": "原表达",
      "replacement": "修改表达",
      "type": "grammar | naturalness | tone",
      "explanationZh": "准确的中文说明"
    }
  ]
}
```

### 中文或混合文本优化

```json
{
  "outputLanguage": "zh | en",
  "improvedText": "优化后的完整文本",
  "changes": [
    {
      "original": "原表达",
      "replacement": "修改表达",
      "type": "clarity | naturalness | tone | structure",
      "explanationZh": "中文说明"
    }
  ]
}
```

## 评分标准

总分 100；质量占 85，性能和成本仅占 15。

| 维度 | 权重 | 说明 |
| --- | ---: | --- |
| 含义与事实忠实度 | 25 | 不改变人名、日期、数字、技术术语、承诺强度 |
| 可直接发送性 | 20 | 无需用户再次重写 |
| Slack/WhatsApp 自然度 | 15 | 简短、口语化、不过度正式 |
| 语法与解释准确性 | 15 | 优化正确，且不把风格偏好说成语法错误 |
| 建议回复合理性 | 10 | 不虚构信息、不制造额外承诺 |
| 延迟 | 10 | 首 token 与完整结构化结果耗时 |
| 成本 | 5 | 按实际输入/输出用量计算 |

### 一票否决问题

出现以下任一问题应单独记录，不被平均分掩盖：

- 改变日期、数字、URL、人名占位符或技术名词。
- 擅自承诺交付时间、同意方案或完成任务。
- 英文优化引入新的语法错误。
- 中文回译没有忠实反映生成的英文。
- 输出无法稳定满足 JSON 契约。

## 评测流程

1. 收集并匿名化 30 条真实案例。
2. 确认三个 provider 的具体模型名称与版本。
3. 在本机配置 API Key，不通过聊天发送密钥。
4. 对每个模型运行相同案例并记录原始输出、token、延迟和估算费用。
5. 随机打乱并隐藏模型名称，生成 A/B/C 对比表。
6. Kris 对每条案例选择最佳结果，并标记不可接受的问题。
7. 汇总按任务拆分的胜率和加权分，不只看一个总分。
8. 决定默认模型；三个 provider 都继续作为用户可配置选项保留。

## Provider 支持决定

- MVP 同时支持 DeepSeek、豆包和 OpenAI。
- 三者共用统一的请求/结构化响应抽象，但各自拥有 provider preset、模型配置和 Keychain 凭据。
- 在三者都能通过相同契约完成 Translate 和 Improve 后，才执行质量盲测并选择默认模型。
- 即使选出默认模型，也不删除另外两个 provider。

## 当前凭据状态

- OpenAI：本机 Hermes 已检测到配置，可用于后续评测。
- DeepSeek：尚未在 Hermes 环境检测到配置。

## 预期交付物

评测完成后生成：

- `eval/cases.jsonl`：匿名化输入与任务类型。
- `eval/raw/<provider>.jsonl`：原始模型结果、延迟和用量。
- `eval/blind-review.md`：隐藏 provider 名称的 A/B/C 人工评审表。
- `eval/report.md`：分任务胜率、错误类型、延迟、成本和最终建议。
